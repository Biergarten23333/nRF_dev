# DECISIONS — R4

### D40 — Stopped at the permission denial instead of routing around it

A1/A2 need writes to the NCS install. The classifier refused. I did not retry
with a different tool: the guard is about the destination, not the tool, and
using Edit to do exactly the refused write would be circumvention rather than
the "reasonable alternative" the refusal allows. Reported instead.

### D41 — My first site enumeration was wrong, and the fix was to generate it

I wrote a 16-entry site header from a `head -20`-truncated grep. There are **23**
(7 in `adv.c`, 16 in `conn.c`). `bsf_v45_conn_sites.h` is now generated by
enumerating the sources, and says so in its header, so the next person cannot
inherit a hand-miscounted list. `BSF_V45_CONN_SITE__MAX` is 32 for headroom.

### D42 — A1's marker goes in CH_TX_WORK, determined not assumed

`DATAFLOW_MAP.md:15,54-60` puts `tx_processor` on `k_sys_work_q`, and `conn.c:75`
states that file owns `BSF_V45_CH_TX_WORK` for exactly that context. Single-writer
holds, so the mark is legal there.

### D43 — Split A1 into origin and consequence

`BSF_V45_TX_SEND_FAIL` (arg0=err, arg1=which of `send_buf`'s three failure
returns) and `BSF_V45_TX_FATAL_DISCONNECT` (arg0=err, arg1=uptime) are separate
stages. "The link died because a send failed" and "the send failed because X"
are different facts and only the second is actionable.

### D44 — A2 records into atomics, not a trace channel

`bt_conn_set_state()` is reached from several threads, so a channel mark would
violate the single-writer rule and be dropped as a writer mismatch. The call
sites write a plain struct plus a saturating per-site counter, which is
context-safe from any thread and is what "one word plus a counter" asked for.

### D45 — N = 320 for CAUSE_CONN_RELEASED

A real disconnect clears `ble_connected` from the callback within milliseconds,
so an honest race is a handful of calls. At the measured ~32 notifies/s, 320 is
~10 s — two orders of magnitude past any race, still twice as fast as the 20 s
dwell arms, and the 2026-08-09 wedge produced 19412 consecutive failures, a 60x
margin.

### D46 — Schema 5 was bumped before its consumer landed

`counters[32]` was exactly full, so no new counter could reach the corpse at all
(`v45_snapshot_counters()` clamps to `ARRAY_SIZE` and would have dropped it
silently). Growing it and adding the conn-release evidence is a layout change and
takes a number. But the evidence it carries comes from A2, which is blocked, so
the bump currently leads its purpose. Recorded rather than hidden; reverting is a
live option next round.

### D47 — Reported the failing decoder self-test rather than leaving it quiet

`test_bsf_v45_decoder.py` fails with `IndexError` after the schema-5 change: its
synthesised core was updated, its DWARF-offset model and `idle` fix-up were not.
A failing test that is mentioned is recoverable; a failing test that is not
mentioned is how the last three rounds each found a test validating the wrong
artefact.

## R4 CONTINUED — after SDK write authorisation

### D48 — KEPT schema 5 rather than reverting to 4, because A2 landed this round

The instruction was to revert to 4 and bump once after A2, unless keeping it is
cheaper. Keeping it is cheaper, and the reason is that A2 is **done in this same
build**: `conn_release` and `conn_site_count[]` are filled by the 24 site markers
and captured into the corpse, so schema 5's consumer exists in the same image
that defines it. Reverting to 4 and re-bumping to 5 within one round would be
pure churn — two layout changes, two decoder updates, two test updates, and two
opportunities to get an offset wrong — to arrive at exactly the layout now built
and gated.

The original objection was sound and I do not dismiss it: last round the bump led
its purpose, which is a real smell. It no longer does.

### D49 — `counters[32]` was exactly full, which is why schema had to move at all

Not a stylistic bump. `v45_snapshot_counters()` clamps to `ARRAY_SIZE(counters)`,
so with 32 of 32 used, every new counter would have been **silently dropped from
the corpse** while incrementing happily in RAM. The five R4 counters would have
existed and been invisible. Grown to 40.

### D50 — Three layers against the silent no-op, not one

The requirement was that a missing or mismatched SDK instrumentation fails the
build. The existing CMake gate already ran `sdk_patch.sh verify`, so hash drift
was covered; what was NOT covered is the case that actually bites — the header
unreachable from the SDK translation units specifically, where the app compiles
and only the marks vanish. So the `__has_include` no-op fallbacks were replaced
with `#error`, and a `BSF_V45_SDK_PATCH_VERSION` stamp was added to
`<zephyr/bluetooth/conn.h>` and checked in `bsf_v45.c`.

Consequence accepted and stated: while the patch is applied, another project
building against this shared SDK gets a hard error instead of silent no-ops.
That is the correct trade — the patch manager exists to revert — but it is a
behaviour change outside this repository and should not be discovered by
surprise.

### D51 — Two more wrong site counts before the generated one

16 (truncated grep), then 23 (pristine sources), then **24** — generated from the
PATCHED sources, which are what compile. The existing v45 patch adds a
`bt_conn_set_state` site of its own, which is why pristine undercounts. The
header now says all of this in its own comment so the next person does not
re-derive it from the wrong tree.

### D52 — RTT is probe-gated, correcting my own claim

I previously described attaching an RTT reader as not needing the probe. Wrong:
`jlink_rtt_transport.py` runs over J-Link. It is in
`SWD_WEDGED_BOARD_RUNBOOK.md` as an OPTIONAL step, explicitly under the same
`PROBE GO` rule, and has **not** been executed.

### D53 — Fixed the decoder self-test rather than leaving it failing

Three schema-4 assumptions survived the schema-5 change: the synthesised core's
tail, `decode_image()`'s bank offset (it used a fixed `SZ["core"]`, so it looked
for the first bank 76 bytes short and reported "no banks" — a decoder bug wearing
a corpse-shaped disguise), and four size constants in the test itself. All four
now derive from `_core_size(schema)`.

## SEGMENT 1 AND THE UNATTENDED BLOCK

### D54 — The first real corpse caught a defect I had just introduced

`bsf_v45_conn_rel` and `bsf_v45_conn_site_count` are `.noinit` and were
initialised nowhere, so the first boot after a flash read whatever was in that
RAM. The corpse showed per-site counts at indices 24/26/27/29 when only 0..23
are compiled, and a `conn_release` that looked entirely plausible
(`site=0 old=0 new=5 total=4`) and meant nothing.

This is precisely what `bsf_v45_corpse_decode.py`'s own header warns about, and
I walked into it. Fixed by tying validity to the corpse's own validation --
`bsf_v45_early_init()` clears both when the CORE fails to validate -- which needs
no layout change and no schema bump, and is correct because if the CORE did not
survive, nothing else in `.noinit` did either. The decoder now also refuses to
present a site id beyond the compiled set as a finding, and marks it SUSPECT.

Rebuilt as `b306-v45r6-*`; **segment 2 flashes r6, not r5**. The board keeps r5
for the remaining val-based tests because A's gate (retention + banks) already
passed on it and none of C/D/T2/negative reads A2 data.

### D55 — Recomputed C's rates against the node clock after nearly reporting nonsense

Host timestamps gave `valid_frames` 47.6 Hz and `notify_ok` 179/s -- impossible
for this link. The master's CDC delivers records in backlog bursts, so host time
compresses. Against `node_ms` it is 8.34 Hz and 31.4/s, matching expectation and
every earlier measurement. Same trap as the T1 "timeline" misread; the rule is
now simply: rates come from the node's clock, never from host arrival times.

### D56 — Negative test substituted, because the master cannot unsubscribe

D2 proposed unsubscribing to prove the detector disarms. The Fusion Master has
no unsubscribe or CCC-write command and does not call `bt_gatt_unsubscribe` at
all, so that path needs a DK firmware change and was not authorised.

Substituted the `producer_alive` arm condition instead: stop the beacon, watch
`armed` go 1 -> 0, confirm no capture, restore, watch it return to 1. It tests
the same property -- the detector refuses to fire when a precondition fails --
and it is arguably a better test now that `armed` is directly observable, which
is itself an R4 addition.

### D57 — T2 variant 1 is INCONCLUSIVE; the board reset and I could not name the cause

`V45 HANG` armed, and within the 40 s window the board reset: `reset_reason=4`
(SREQ, a software reset), `up_ms` restarted, the hang flag cleared (`.bss`), and
no v45 corpse survived (`present=0 seq=0`).

Ruled out by direct measurement, not by argument:

| candidate | evidence against |
|---|---|
| v41 stall recovery (`main.c:1546`) | `STALL STATUS rc=0 rcc=0/0/0/0 alarm=0/0` -- never fired |
| v45 reboot, BTRX monitor, ring ISR | all budget-gated; `CORPSE STATUS reboot_owner=3` -- the budget has been held by v45 since A.1, so every take is denied |
| MCUboot confirm timeout (`main.c:2662`) | `BOOT CONFIRM STATUS confirmed=1 required=0` |
| Zephyr fatal-error reset | `CONFIG_RESET_ON_FATAL_ERROR is not set` -- a fatal error halts |
| `REBOOT` vendor command | not issued |

So a software reset occurred that none of the known paths explains. **T2 variant
2 was NOT run**: a second uninterpretable reset adds nothing.

The log would name it -- `LOG_ERR` from whichever path called `sys_reboot`, or a
fatal-error dump -- and the log needs an RTT reader, which needs the probe DURING
the test. That does not fit the current two-segment structure, so it is raised
rather than worked around.

## 2026-08-09 — watchdog beats detector; fix the watchdog side, not T2

**Fork.** The `V45 HANG` re-run reset BSF6C53 via RESETREAS.DOG, not a software
reset, and took the corpse with it. Two ways out: soften the injection so it
stops killing the system workqueue, or change the watchdog side.

**Decision (operator, explicit).** Do NOT touch the T2 injection. It is the only
thing that reproduces a syswq death, and softening it would leave the campaign
with no validation tool for the class. The problem is not that T2 fails; it is
that a 30 s watchdog eats the corpse of any REAL syswq wedge and the node then
looks identical to one where nothing happened.

**Done:** dwell 20 s -> 12 s; one `wdt_feed()` inside `v45_capture()`; `.noinit`
watchdog witness reported on `V45 STATUS` (`dog=`, `dog_dwell=`, `dog_age_ms=`,
`dog_tick_ms=`). Watchdog timeout deliberately NOT extended -- that feed is the
diagnostic. Structural non-coverage written up in
DETECTOR_COVERAGE_SCORECARD.md, not as a footnote.

**Also fixed, all found by measurement rather than review:**
- `rtt_t2_capture.py` compared `up_ms` (ms) to `window + 15` (s). Reported
  `NOT REPRODUCED` for a run that HAD reproduced. Fifth false verdict from a
  reading tool this campaign; runbook now requires a one-off hand-check of any
  new reading script against raw data before it is believed.
- `test_v45_source_contract.py` hashed the SUPERSEDED patch file and called a
  correct `PATCH_SHA` stale. Taking its advice would have broken sdk_patch.sh's
  own integrity check. Filename is now read out of sdk_patch.sh.
- `test_v45_source_contract.py` still expected schema 3; corpse.h is at 5.
- `test_bsf_v45_detector.c` had been red since R4 (harness never moved
  `notify_ok_total`), so arm C and CONN_RELEASED shipped untested. Fixed,
  covered, and the dwell is now pinned by a test instead of copied into ten.
- Flashing removed from the RTT segment. The 2026-08-09 flash failed with
  `Failed to erase sectors` after pylink left the core in a debug state and
  J-Link fell back to VECTRESET. One tool per contact.

**F3b result.** No pool leaking: every pool `out=0`. But the deepest any pool
was ever driven is 2 buffers, because the earlier T2 watchdog reset had already
wiped the usage history before the sample was taken. Ordering F3b ahead of the
segment-2 T2 protected it from THAT reset, not the previous one. The row-[1]
`ref=168` question is still open and needs a sample from a board with real
uptime under load. New tool: `tools/swd/parse_pools.py`.

## 2026-08-09 — B acceptance: reboot OBSERVED, and v45 owns it

**The reboot is no longer an inference.** `RING boot=2` -- boot_id incremented
from 1 (the flash reset) to 2. `init=retained` -- `.noinit` survived that
reset, so RAM retention itself is intact.

**v45 caused it.** `CORPSE ... reboot_owner=3`, and
`BSF_V45_REBOOT_OWNER = 3u` (bsf_v45.c:155). The shared one-per-power-cycle
reboot budget was taken by the v45 detector, which only happens on
`v45_budget_take(BSF_V45_REBOOT_OWNER)` inside the capture path (bsf_v45.c:1033).

**The capture started.** `RING frozen=1 reason=1 fidx=510 fms=38743`. Freezing
the trajectory ring is step 2 of `v45_capture()`.

**And the corpse still did not validate.** `V45 present=0`, on a boot where
`.noinit` demonstrably survived.

So the chain is: detector triggered -> capture began -> ring frozen -> reboot
budget taken -> board rebooted -> `bsf_v45_core_validate()` returned false.
`dog=0` excludes the watchdog; this was v45's own `sys_reboot`.

**Fork: is this a REGRESSION or a never-tested path?** Recorded as UNRESOLVED
rather than assumed. `present=1` appears in earlier logs
(stage_b_step2_20260808/T1_force) but via the `V45 FORCE` path, which captures
without a real trigger. Whether a corpse has ever survived an actual REBOOT is
not established by anything on disk. B acceptance has never before run far
enough to test it, so "the fourth F1 instance" is the likely but unproven
reading; it may equally be the first honest test of a path that never worked.
Resolving this decides whether the lifetime sweep is looking for a new defect
or an old one.

## 2026-08-09 — FORK RESOLVED: the v45 corpse has NEVER survived a reboot

Swept every `present=1` on disk (76 readings across 12 files).

**Every single one is `cause=4` = BSF_V45_CAUSE_FORCED.** No real detector
trigger has ever produced a readable v45 corpse, on any build, ever.

**None was read after a reboot.** Classified by walking each file in order and
watching for `up_ms` going backwards: 0 after a reboot, 5 with no reboot in the
file, 71 in `commands_*.json` files that carry no `up_ms` at all. The long-blind
readings (`blind_ms=60946`, `93346`) are decisive on their own: `blind_ms`
counts from boot, so a corpse still present 93 s into a boot with no reboot in
between is a corpse that never faced one. Its FORCE did not reboot at all --
consistent with the reboot budget already being spent, since
`out.reboot = (trigger_count == 0u)`.

**Therefore tonight is NOT a regression.** It is the first honest end-to-end
test of "a corpse survives a real reboot", and it failed. The census must hunt
an OLD defect, present since the mechanism was written -- not something schema 5
or the dog witness introduced. Both remain suspects only as ordinary code, not
as prime ones.

This also re-reads the earlier T1 result: `present=1` after `V45 FORCE` proved
capture and export worked. It never proved retention, and was recorded as
though it did.
