# 20260330 Goal — Phase 2 Anchor-Side Evolution Plan

Date: 2026-03-30  
Owner scope: Anchor-side architecture evolution (Phase 2 roadmap + Phase 2.1 start)

## 1. Background

Current verified prerequisite state:
- Anchor role baselines are confirmed usable/stable:
  - `master` (`build-anchor-<X>-master-full`)
  - `matrix` (`build-anchor-<X>-matrix`)
  - `responder` (`build-anchor-<X>-tag`)
- Flashing layer has been hardened for deterministic SN-pinned behavior.
- Ref115 BLE calibration strict baseline exists and is proven:
  - strict threshold pass (`cm_records=504`)
- Ref115 idle guard is available and validated.
- Stage3 / Tag127 work is currently frozen and not part of anchor Phase 2 execution.

Why change now:
- Current model still depends on separate role build families and repeated reflashing.
- Long-term direction is closer to PANS/DRTLS-style operation:
  - one base firmware/runtime
  - mode/role selected by configuration/control plane
  - OTA + runtime control replacing repeated manual role image switching.

## 2. Phase 2 Overall Objective

Transition from separate anchor role build families into a unified anchor runtime stack:
- one unified anchor base runtime/build foundation,
- role-selectable behavior (`master`, `matrix`, `responder`),
- later OTA-deliverable as standard anchor image,
- later BLE/runtime configurable role switching,
- later 52840 control-plane orchestration and verification.

## 3. Phase 2 Sub-Phases

### Phase 2.1 — Unified anchor runtime structure (start now)
- Merge role entry structure into one anchor base runtime.
- Keep one active role at startup (`master` / `matrix` / `responder`).
- Preserve existing known-good behavior for each role.
- Keep startup signatures explicit for role confirmation.
- Deliver fresh build/run evidence for unified role dispatch.

### Phase 2.2 — OTA baseline for unified anchor image
- Make unified anchor runtime the standard OTA-distributable anchor image.
- Remove operational dependence on maintaining separate role-family images.
- Validate OTA update reliability for anchor image lifecycle.

### Phase 2.3 — BLE/runtime role configuration
- Add role-selectable runtime config path (without rebuild).
- Define role config schema and persistence model.
- Add safe role transition behavior and startup/readback markers.

### Phase 2.4 — 52840 control-plane integration
- Add anchor discovery / command / role assignment from 52840.
- Add role state confirmation readback and operation logs.
- Build deterministic orchestration path for matrix/responder transitions.

### Phase 2.5 — End-to-end autopositioning integration
- Integrate unified anchor runtime flow with matrix + Ref115 BLE calibration pipeline.
- Standardize full orchestration sequence and acceptance gates.
- Ensure production workflow does not regress current validated baselines.

## 4. Today's Immediate Implementation Target

Start **Phase 2.1 only**:
- Implement unified anchor runtime role-dispatch structure.
- Preserve current verified role behavior.
- Build fresh artifacts and run focused validation for role bring-up.
- Do not implement OTA/BLE role switching control yet.

## 5. In-Scope vs Out-of-Scope (Today)

### In scope now
- Unified anchor base runtime/build structure.
- Role dispatch (`master`, `matrix`, `responder`) in one runtime path.
- Startup signature clarity and behavior parity checks.

### Out of scope for today
- OTA role switching implementation.
- BLE `SET_CONFIG` role switching implementation.
- Full 52840 anchor orchestration implementation.
- Stage3 / Tag127 work.
- Unrelated tag-side architecture changes.

## 6. Success Criteria

### Phase 2 overall success criteria
- Unified anchor runtime can be deployed as standard image.
- Role selection no longer requires maintaining separate role-family builds.
- Role switching is controllable and verifiable through BLE + 52840 control plane.
- Full autopositioning flow runs on unified anchor runtime without baseline regressions.

### Today's success criteria (Phase 2.1 start)
- Unified anchor runtime role-dispatch structure exists in code.
- One unified build path can bring up `master`, `matrix`, `responder` behavior.
- Startup signatures explicitly identify active role.
- Fresh build and focused runtime validation evidence recorded.

## 7. Design Principles / Constraints

- Do not regress already validated anchor baselines.
- One runtime, one active role at a time.
- Keep role logic explicit and testable (not hidden monolith behavior).
- Preserve clear startup signatures for diagnostics.
- OTA/BLE role switching comes after runtime unification, not before.
- Keep implementation grounded in verified baseline behavior and evidence.

## 8. Relationship to Later Platform Direction

Phase 2 is the anchor-side bridge toward long-term runtime architecture:
- unified base firmware,
- OTA as deployment standard,
- config-driven operation,
- 52840-led orchestration,
- reduced dependence on repeated manual reflashing for role transitions.
